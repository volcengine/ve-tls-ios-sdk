# 性能参考

性能结果与设备、系统、日志大小、持久化方式和网络条件强相关。以下实测数据用于估算资源开销，
结果用于选型和配置参考，不作为吞吐上限或 SLA。

### 读表说明

- MB 使用十进制：`1 MB = 1,000,000 bytes`。
- CPU 和 RSS 为整个测试 App 进程的指标，包含测试代码、运行库和 SDK；没有扣除空 App，
  因此不表示 SDK 的独占 CPU 或增量内存。CPU 为 `getrusage` 的 user + system CPU 时间增量
  除以测量时长再乘 100，100% 表示占满一个逻辑核；输入构造时间也计入其中。
  RSS 通过 `task_info` 的 `resident_size` 约每秒采样，峰值是采样峰值。
- `add P99` 从测量窗口内逐条调用的纳秒耗时排序，取第 `ceil(样本数 × 0.99)` 个样本，
  再换算成微秒；不包含调用前的日志构造时间。
- 原始接收速率按 `add` 成功的业务 key/value 字节计算，不是服务端写入确认或压缩后的网络流量。
  例如 500 条/秒 × 700 B × 60 秒 = 21 MB/min；实际窗口长度的小幅波动计入计算后，
  仍四舍五入为表中数值。
- 单轮数据不适合据此断言 buffered 比 memory 更省内存，也不表示 500 条/秒是吞吐上限。
  以上是真机结果，未混入 Simulator 或原生 macOS 结果。

## 在自己的负载下测量

优先使用真实字段组合，固定日志字节数、速率、批次和持久化配置。记录 SDK 版本、设备型号、
系统、Xcode、构建模式和网络条件。建议使用 Release 构建，预热后再采样；版本间比较时重复
运行并报告中位数与波动范围，不只选择最好的一次。

至少观察：

- 本地接收/拒绝数、成功/失败批次回调，以及 `close` 结果；
- `add` P50/P99、进程 CPU、RSS 和 WAL 目录大小；
- 实际接收速率，以及通过事件 ID 核对的服务端唯一日志数；
- 弱网和离线恢复时的拒绝、重复和缺失情况。

三种字节口径应分别记录：

| 口径 | 计算来源 | 含义 |
|---|---|---|
| 业务原始接收速率 | 成功接收的 key/value UTF-8 字节 / 时间 | 业务输入，不是服务端写入确认 |
| 成功批次字节速率 | 成功回调的 `rawBytes` / 时间 | 未压缩批次字节，不等同于业务字段字节 |
| 压缩负载速率 | 成功回调的 `compressedBytes` / 时间 | 压缩 body 字节，不含 HTTP/TLS 开销 |

换算为 MB/min 时，字节数除以秒数，再乘 60、除以 1,000,000。回调可能晚于提交窗口，
不要将整个进程的回调总量与某个较短窗口的输入量直接比较。

## 配置调整

- 批次较小时，可提高 `maxLogCount`、`maxRawBytes` 或 `linger`，减少请求次数；
- 希望日志更早发出时，可降低 `linger`；它影响等待封批的时间，不是 `add` 的同步执行时间；
- 网络和 CPU 有余量时，可逐步提高 `sendConcurrency`，同时检查资源占用和错误；
- 长时间离线时，关注 WAL 容量、磁盘空间和恢复行为，不宜只增大内存缓冲区；
- `.sync` 在更强的本地持久性和写入延迟之间取舍，适用于明确需要同步落盘的场景。

每次只调整一个主要参数。默认值、范围和单位见[配置参数](../reference/configuration.md)。
